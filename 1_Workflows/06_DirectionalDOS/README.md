## Directional DOS Analysis

**Use:** Create and analyse a spatialy reolved partial phonon density of states, mapping the average pDOS akin to [Böger *et al*](https://doi.org/10.1021/jacs.4c12034) and extracting useful descriptors and direcional pDOS curves.

## Workflow:

**Prerequisites:** 
- The `FreqBallz_v7.py`, `FreqSiteFinder_v4.py` and `FreqConfigGen.py` must be on `PATH` or in the calculation folder
- The following python packages need to be importable: `PhonoPy`, `h5py`, `PyYaml` and `numpy`
- optionally, for migration network support `pymatgen` needs to be available
- optionally, `pyvista` needs to be installed for visualization
- optionally for the MPI parallelization to work you also need `mpi4py` available
- Optionally, migration pathways can be provided to the script to explicitly investigate them the example here uses `SoftBV2Path` to generate them

**Folder Setup:**
- `POSCAR`     &rarr; fully relaxed strucutre, make sure to use the same one as for your `PhonoPy` run
- `FORCE_SETS` &rarr; second-order force constants from a previous `PhonoPy` run, check that these are stable
- `BORN`       &rarr; optionally to compute the frequencies with NAC active, to write see [04_LO-TO](https://github.com/Kit553/PhononTools/tree/main/1_Workflows/04_LO-TO)
- `conductionPath.yaml` &rarr; canonical migration-path description

**These files will be generated by the workflow:**
- `conf.yaml`  &rarr; recipe for the `FreqBallz_4_1.py` script to work
- `direction_families.yaml` &rarr; ranking for each direction to designed how well they align with migration paths
- `results/directional_pdos.h5` &rarr; result file

### 0. \[Optional\] Supplying the Migration Path:

The migration pathways are optional to supply to the script, they are separated from the normal FreqBall calculation. Any method can in principle be used to obtain migration minima, saddle points and their connectivity, provided their result can be converted to the canonical schema:

```yaml
schema: freqball_conduction_path_v1
coordinate_system: fractional

source:
    method: YOUR_METHOD
    file: source_file_or_description

energy_minima:
  - index: 0
    type: i1
    multiplicity: 1
    energy_ev: 0.0
    position: [0.0, 0.5, 0.0]

  - index: 1
    type: i1
    multiplicity: 1
    energy_ev: 0.0
    position: [0.0, 0.5, 0.0]

saddles:
  - index: 0
    type: i1
    multiplicity: 1
    energy_ev: 0.0
    position: [0.0, 0.25, 0.0]

paths:
  - index: 0
    from_minimum: 0
    to_minimum: 1
    saddle: 0
    from_type: i1
    to_type: i1
    saddle_type: s1
    from_energy_eV: 0.0
    to_energy_eV: 0.0
    saddle_energy_eV: 0.35
    boundary_cross: [0, 0, 0]
```

**Important Points:**
- coordinates must be fractional/reduced coordinates
- `energy_minima`, `saddles` and `paths` are required
- the `paths` block must contain the explicit minimum &rarr; saddle &rarr; minimum connectivity
- `boundary_cross` identifies the periodic image of the target minimum if the hop crosses a unit-cell boundary
- the `source` block is provenance only, FreqBall does not require a particular BVS or migration-path package; anything goes

`FreqSiteFinder.py` uses the explicit connectivity in `paths`; it does **not** guess migration directions from the nearest saddles!

##### 0.1 Example Source *SoftBV*/*BVPA*

*SoftBV* is one of the possible ways to generate the migration paths, this section will be updated as soon as helper script for different methods (FullProf, MEntropy) are available. For now only *SoftBV* is supported via the `BVPARun_v2.py` script.

For the *SoftBV* workflow you will need:
- a structure `.cif` file; ideally this is converted from your `POSCAR` so the structures match exactly also make sure that the ions get their correct charges
- the corresponding *SoftBV* potential-map `.cube` file; obtain this via the normal *SoftBV* gui
- a working installation of *SoftBV*, note the location of the `bin/BVPA_132.exe`

The way *SoftBV* is set up requires you to run it from its canonical location `<SoftBV root>/bin/BVPA_132.exe` not from the `bin/` directory. For the provided script to work, set the shell variable with:

```bash
export SOFTBV_ROOT='/mnt/c/Users/USERNAME/path/to/SoftBV'
```

or supply it directly with the `--softbv-root` flag in the cli. Then run `BVPA` with the provided wrapper `BVPARun_v2`:

```bash
python ~/bin/BVPARun_v2 \
    --cif YOUR.cif \
    --cube YOUR.cube \
    --ion Na1+ \
    -o BVPA
```

the respective arguments are:
- `--cif` &rarr; structure used by `BVPA`
- `--cube` &rarr; corresponding potential-map file
- `--ion` &rarr; mobile ion including charge
- `--o <PATH>`/`--output-dir <PATH>` &rarr; directory in which the generated `BVPA_*` files are collected
- `--softbv-root <PATH>` &rarr; optional alternative to setting the `$SOFTBV_ROOT` variable
- `--exe <NAME>` &rarr; optional overwrite for the name of the executable; default name is `BVPA_132.exe` but versions may vary

The output should look like:
- `BVPA_summary.txt`
- `BVPA_gui.csv`
- `BVPA_events.txt`
- `BVPA_rp.csv`
- `BVPA_stdout.txt`
- `BVPA_stderr.txt`

Check through the error files before continuing. Common errors include missing database files (`BVPA` was run in the wrong directory make sure to call it at `bin/BVPA_132.exe` the lookups are relative to this `PATH`) and not recognizing the provided ion type (include charges in your `.cif` file)

Once the output looks clean continue by converting the information from the output directory to the `conductionPath.yaml` wth

```bash
python ~/bin/SoftBV2Path BVPA -o conductionPath.yaml
```

Or if for some reason only the summary file is available:

```bash
python ~/bin/SoftBV2Path BVPA/BVPA_summary.txt -o conductionPath.yaml
```

Use the `--strict` flag if you want to make sure all information of the `BVPA` output is written to the final `.yaml`

##### Building atom-local direction families:

`FreqSiteFinder_v4.py` combines the canonical migration path with the actual structure and constructrs direction families separately for every mobile-ion site.
For an exemplary system with mobile Na ions and Sb-centered tetrahedra use:

```bash
python FreqSiteFinder_v4.py \
    POSCAR \
    --path conductionPath.yaml \
    --mobile Na \
    --tetra-center Sb \
    -o direction_families.yaml
```

For other systems replace mobile ion species and the center atom for your polyanions as appropriate. Multiple mobile ions and tetrahedral species can be provided with one flag.

The generated direction familes generally contain:
- **BVS** &rarr; path-derived mobile-ion-site to connected migration-saddle directions.
- **NaNa** &rarr; mobile-ion-site to connected mobile-ion-site directions
- **TetCenter** &rarr; mobile-ion-site to nearby tetrahedral-centre directions
- crystallographic equivalence information for the mobile-ion sites
- provenance linking the vectors back to migration minima, saddles and paths

**BVS** and **NaNa** are reduced separately by axial angular similarity. 

**Useful stuff:**
- `--path-match-tol <float>` &rarr; maximum distance in Å between migration minimum and the corresponding mobile-ion structure site
- `--angle-tol <float>` &rarr; axial angular tolerance used to remove redundant directions
- `--tetra-nearest <int>` &rarr; number of nearny tetrahedral centers retained per mobile ion
- `--symprec <float>` &rarr; symmetry tolerance
- `--view` &rarr; with pyvista and the helper script installed, use this option to look at the directions interactively

Always inspect the printed minimum-to-site mapping. Large match distances normally mean the migration-path structure and the `PhonoPy`/`POSCAR` structure do not correspond closely enough.

### 1. Generating the `config.yaml`

The recommended way to create the v7 configuration is `FreqConfigGen.py` rather than writing it manually.

A reproducible explicit example is:

```bash
python FreqConfigGen.py . \
    --phonopy-yaml phonopy_disp.yaml \
    --force-sets FORCE_SETS \
    --born BORN_Symm \
    --families direction_families.yaml \
    --species Na \
    --mesh 15 15 15 \
    --directions 1000 \
    --freq-min -2 \
    --freq-max 25 \
    --pitch 0.01 \
    --sigma 0.05 \
    --low-cutoff 2.0 \
    --result results/directional_pdos.h5 \
    -o config.yaml
```

`FreqConfigGen.py` can auto-detect common filenames. It explicitly searches for:
- `phonopy_disp.yaml` / `phonopy.yaml`
- `FORCE_SETS` / `force_sets`
- `direction_families.yaml`
- `BORN_Symm` / `BORN_SYMM` / `BORN`

Use `--no-born` when NAC should intentionally be disabled.

**Current Configuration Blocks:**

A generated `config.yaml` resembles:

```bash
schema_version: 1

phonopy:
  phonopy_yaml: phonopy_disp.yaml
  force_sets: FORCE_SETS
  born: BORN_Symm
  mesh: [15, 15, 15]

sampling:
  n_directions: 1000
  freq_min: -2
  freq_max: 25
  freq_pitch: 0.01
  sigma: 0.05

direction_families_file: direction_families.yaml
direction_family_match_tolerance_A: 0.02

ions:
  species: Na

output:
  file: results/directional_pdos.h5
  spectra_dtype: float32

selection:
  low_freq_cutoff: 2.0
```

1. phonopy:
This section store the mandatory file location information.
    - phonopy_yaml: `path/to/phonopy_disp.yaml`
    - force_sets: `path/to/FORCE_SETS`
    - born: `path/to/BORN`
    - mesh: \[$N_{\mathrm{x}}$, $N_{\mathrm{x}}$, $N_{\mathrm{x}}$\] &rarr; Brillouin zone integration grid size in *x*, *y*, *z* direction

2. sampling:
This section defines how the average frequencies are computed.
   - n_directions: 1000 &rarr; number of regularly spaced directions over the Ball
   - freq_min: 0.0      &rarr; minimum of considered frequency; can be usefull if small negative dips occurr, should not be used to disregard real dynamic instabilities
   - freq_max: 20.0     &rarr; maximum freqeuency considered
   - freq_pitch: 0.02   &rarr; frequency pitch as used by `PhonoPy`
   - sigma: 0.05        &rarr; smearing factor as used by `PhonoPy`

3. selection:
Here optional additional metrics are described.
    - low_freq_cutoff: 2.0                  &rarr; frequency cutoff defining the low-frequency region
    - n_high_avg: 3                         &rarr; number of high average frequency directions considered per ion
    - n_low_avg: 3                          &rarr; number of low average frequency directions considered per ion
    - n_high_lowfreq: 4                     &rarr; number of directions with high low-frequency weight considered per selected ion
    - max_selected: 20                      &rarr; maximum number of stored representative directions stored in the /selected group
    - min_separation_deg: 12.0              &rarr; minimum angular separation between selected directions; prevents the extrema to bundle up
    - mode_extrema_overlap_fraction 0.10    &rarr; fraction of the maximum directional overlap 
    - mode_extrema_min_abs_overlap 1.0e-10  &rarr; absolute lower bound for meaningful directional mode overlap

5. direction_families_file:
This points to the atom-local reference directions generated by `FreqSiteFinder_v4.py`.
    - `ions:`  &rarr; selected primitive-cell atoms may be specified in three ways: `species: Na` selects all atoms of one species; `indices: [int, int]` list of indies; `mode: direction_familes` searches the `direction_families.yaml` file

6. output:
This section defines the output of your calculation.
    - file: `path/to/output_directional_dos.h5`
    - spectra_dtype: float32                  &rarr; reduce Output to 32 based float, change to 64 based only when you want to brick your PC

### 3. Running the calculation:

Once the `config.yaml` file has been set up, the calculation can be run either locally via:

```python
python FreqBallz_v7.py config.yaml
```

Or as a queued job on the cluster via the `job.sh` script.  
It is generally preferred to run on the cluster as the workload and file size can quickly become immense with extended systems or very fine grids. If you just need to check a few named directions, local runs can be done though. When running on the cluster calling the script through `python` is preferred over executing the file itself directly, it avoids exec-bit issues on the compute nodes. 

###### A Note on Parallelization:

The MPI parallelization is extremely important to reduce the runtime of this job by orders of magnitude. On some node configurations, the default OpenMPI communication backend can be unstable, in particular when high-performance interconnect backends or shared-memory single-copy mechanisms such as `CMA`, `XPMEM` or `KNEM` are selected. To circumvent this specifically request the `ob1` point-to-point messaging layer, disable OpenMPIs single-copy shared memory mechanism `vader` and the `psm2` backend. This conservative MPI setup add to the I/O overhead but prevents crashes from OpenMPI configuration, once the issue if fixed by the Admin team this section will be adapted to reflect the new OpenMPI setup.
 
```bash
export OMPI_MCA_btl_vader_single_copy_mechanism=none

mpirun \
  --mca pml ob1 \
  --mca mtl ^psm2 \
  --mca btl self,vader,tcp \
  -n "$SLURM_NTASKS" \
  python FreqBallz_4_1.py config.yaml
```

If I/O overhead becomes unbearable due to high throughput or extremely extended systems, restrict the job script to only target nodes with known working configuration.

### 4. Inspecting the Output

To make sure that the calculation run was successfull check the `directional_pdos.h5` file, it should contain the following keys:

- /metadata           &rarr; a copy of the `config.yaml` file and provenance information
- /direction          &rarr; list of all computed directions as fractional or cartesian vectors
- /ions               &rarr; stores the ion group
- /frequency_points   &rarr; the frequency grid defining the pDOS spectra
- spectra             &rarr; contains the full pDOS curves for the directions
- /scalars            &rarr; has all the scalar descriptors defined in the selection section of the `config.yaml`   
- mode_extrema        &rarr; stores the extrema directions set in the selection section of the `config.yaml` 
- named_diredctions   &rarr; stores the named directions set in the selection section of the `config.yaml`

Run the included helper script `h5Keys.py` to quickly check that everythings in order.

#### 4. Analysing Output

After finishing the calculation, the output can be analyzed starting from the visual inspection of the mapped average frequencies with the `Ballz_Visual.py` script. This script gives an interactive visualization of the frequency ball and cannot be run on PALMA-II, transfer the result file `directional_pdos.h5` to your local machine then adjust the relevant sections of the script `USER SETTINGS` according to your needs. The most important ones are:

- `h5file`             &rarr; `path/to/directional_pdos.h5`
- `structure_file`     &rarr; `path/to/POSCAR`
- `h5_local_ion_index` &rarr; zero based index of the visualized ion in the selected ion group
- `metric`             &rarr; visualized metric; most commonly `"avg_freq"`; see the list in the file for other options

The remaing parameters are specialized and their use is explained in place in the file.

It opens four windows to control the visualization:
    1. 3D FreqBall Orientation View:
       This is the main window and displays your ion site coloured by average frequency with the surrounding ions being shown as yellow balls to help with orientation, it also includes the frequency scale and a cross to show crystallographic directions
    2. 2D Projection Preview
       This window show a high-quality image of your ion site without any markers etc. it should be used to export the an svg image of the ion to set it safely in your figures
    3. Orientation Controls
       This window changes the orientation of the 2D and 3D interactive viewers to the given orientation matrix; it accurately matches the orientation matrix given by VESTA up to a factor of -1 so sometimes it is necessary to mirror the view to be accurate
       switches between ortographic and perspective views; orthographic prevents distortion due to depth effects while perspective gives nicer figure plots due to depth correction in perspective view focal lenght `f` and camera distance `d` can be adjusted specifically
    4. Metric Marker Toggles:
       This toggles markers for special directions of the system; it shows (if available) the directions of the scalar descriptors define in the selection section of the `config.yaml`

Finally, extract the scalar metrics and relevant pDOS curves with the `BallAnalyzer.py` script. This batch analyzer takes all ions in the `directional_pdos.h5` file and prints out the outputs:
- summary.txt                                   &rarr; quick summary file about the calculation, similar to the `metadata` section of the `h5` file
- rankings.txt                                  &rarr; gives a quick ranking of the important directions by the specified metrics
- direction_descriptors.csv                     &rarr; full list of the directions and the calculated descriptors
- pdos_summary.csv                              &rarr; global average of the pDOS to compare direction resolution; check this against your standard `PhonoPy` run to validate
- pdos_per_atom_mean.csv                        &rarr; conventional atom resolved pDOS from the calculation
- mode_extrema_all_directions.csv               &rarr; match extreme directions to the corresponing *q*-points
- mode_extrema_selected_directions.csv          &rarr; compact overview of the above

If `export_selected_ion_pdos = True`:
- single_ion_pdos/selected_direction_pdos.csv   &rarr; pDOS curves along representative directions for the selected ion
- single_ion_pdos/selected_direction_info.csv   &rarr; metadata of the representative directions
- single_ion_pdos/direction_selection_table.csv &rarr; metadata of all directions from the selected ion to regex

To use the script change the relvant `USER_SETTINGS`, most important among them:
- `h5file`                      &rarr; `path/to/directional_pdos.h5`
- `outdir`                      &rarr; `path/to/output`
- `expected_indices`            &rarr; one-based indices of the ions according to `POSCAR` ordering, important to prevent mismatches
- `pdos_export_local_ion_index` &rarr; zero-based index of the selected ion in the list of ions

The pDOS curves can the be plotted to obtain extremely direction resolved information of the system.
